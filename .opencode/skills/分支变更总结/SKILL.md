# 分支变更总结

分析当前分支从 `master` 分叉以来的所有提交，生成结构化的变更总结。

## 预注入上下文

- 当前分支: !`git branch --show-current`
- 基分支: `master`

---

## 执行步骤

### 1. 获取提交列表

```bash
git log master..HEAD --oneline --reverse
```

### 2. 获取变更文件概览

```bash
git diff --stat master..HEAD
```

### 3. 逐个分析提交

对每个有效提交执行 `git show <hash> --stat --format="%H%n%s%n%b"` 获取：
- 修改的文件列表
- 提交信息中的变更描述
- 业务影响范围

提交信息中通常已包含 `@` 标注的问题分类（如 `fix(media-service)`、`feat(cross-module)`），可直接复用其中的分析。

### 4. 合并同类问题

自动将相同业务领域的提交合并为一个问题条目：

- **同一功能的多轮修复**：如先在原类加 @Transactional，后提取独立 Service → 合并为一个"素材审核修复"条目
- **同一批次的变更**：如新增模型 + 后续 JSON 语法修复 → 合并为一个条目
- **配套变更**：代码变更 + 对应的配置变更 → 合并到对应业务条目

**排除以下提交**：
- Merge 提交（如 `Merge branch 'master' into ...`）
- 纯 K8s 基础设施配置变更（如 terminationGracePeriodSeconds 调整）
- 分支起点提交（信息为 `..` 的无内容提交）
- 纯 Worker 生命周期 / 运维相关变更（不涉及业务逻辑）

### 5. 生成总结报告

按以下格式输出，表格内容使用中文：

```
## 分支 `<branch-name>` 变更总结

| 问题 | 涉及接口 | 涉及业务流程 | 是否涉及前端 | 是否涉及表结构/数据调整 |
|------|---------|-------------|:---:|:---:|
| **问题标题**：简要描述变更内容和原因 | 具体接口路径或「—（内部路由）」 | 受影响的业务流程 | 是/否 | 是/否 |

### 涉及模块

| 模块 | 变更类型 |
|------|---------|
| ... | ... |

### 前端影响

仅列出有前端感知的变更（如接口响应新增字段、API 路径变更）。
```

## 判断规则

| 维度 | 判断依据 |
|------|---------|
| **涉及接口** | 有 HTTP API 变更 → 标注具体方法和路径；仅内部路由/配置 → 「—（内部路由）」或「—（内部基础设施）」 |
| **涉及业务流程** | 标注受影响的业务链路（如"素材审核异步处理链路""图片生成"） |
| **涉及前端** | 接口响应结构变更（新增/修改/删除字段）、API 路径变更 → **是**；其余 → 否 |
| **涉及表结构** | 存在 SQL/DDL 变更（建表、改字段、Flyway 迁移等）→ **是**，并在描述中注明具体变更 |
| **涉及模块** | 只列出需要打包部署的独立微服务（如 task-service、auth-service、novel-promotion-service）。**不包括**：共享库/配置模块（如 common、standards — 随依赖服务打包，无需单独列出）、纯文档目录（如 docs — 不需部署） |

## 输出要求

- 每个问题条目用**粗体标题**开头，后跟冒号和简要说明
- 问题描述要说明**原因和影响**，不只是罗列变更内容
- 同类变更自动合并，避免罗列过多碎片化条目
- 涉及模块部分只列独立微服务（需打包部署的），排除 common、standards、docs 等共享/文档模块
- 涉及模块部分按变更程度排序（变更多的模块在前）
- 前端影响部分如有具体字段变更，说明字段名称和影响方式（纯增量/破坏性变更）
